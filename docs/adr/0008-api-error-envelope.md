# Report every API error as one JSON envelope with a stable code

Every error response under `/api/v1`, including the security middleware, the login rate limit, unknown routes, and wrong methods, is `application/json` shaped as `{"error":{"code":"…","message":"…","field":"…"}}`. Clients decide what to do from `code`, not from the HTTP status or the message: a single 409 used to cover stale versions, reused request keys, duplicate names, and settled bills, and a single 400 "invalid input" covered every validation failure, so a client could not tell whether to reload, fix a field, or send a new key. The code list is part of the API contract; adding a code is a contract change, and renaming or removing one breaks clients.

Domain failures are typed errors in the ledger package (the finance package when this was decided; see ADR 0013), each with a code, a fixed human-readable message, and an optional `field` naming the one input at fault. Transport failures (`forbidden`, `unsupported_media_type`, `method_not_allowed`, `rate_limited`, `internal`) are defined in the HTTP layer. One mapping function in the HTTP layer turns an error into a status and body; it trusts only typed errors, so an untyped failure, including a bare "no rows" from SQLite, is reported as 500 `internal` rather than disguised as a missing record. Messages are fixed text and never echo request values, secrets, or stored data; the server logs only an error-type prefix for 500s.

HTTP statuses stayed as they were when the envelope was introduced, except that correcting or voiding an opening balance or adjustment changed from 409 to 400 `not_correctable`, because it is not a retryable conflict. The `/healthz` endpoint is outside the API and keeps its `{"status":…}` body.
