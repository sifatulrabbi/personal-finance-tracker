# Keep the calculation behind an amount as checked evidence

People often work out an amount before recording it, such as a shop receipt of several items or a bill split. Every amount field in the web client accepts a calculation (`120+45.50+300*2`) and shows its result before saving. We keep the typed calculation only on records, where it explains how an amount was reached: income, expenses, transfers (sent and received amounts), bill payments, opening balances, and balance adjustments (the typed target). Schedule amounts, credit limits, and monthly targets are plans or settings, so they keep only the result.

The amount remains the only financial value. A formula is an optional field stored in the revision payload beside the amount, so it needs no migration, is preserved per revision with its author like every other field (ADR 0002), and never feeds a typed column or a balance (ADR 0012). The server does not trust the client's arithmetic: `internal/money` holds a small exact evaluator (`big.Rat`, no floating point) and `internal/ledger` accepts a formula only when it rounds to exactly the saved amount, else 400 `validation_failed` on the formula's field (ADR 0008). The grammar is deliberately tiny: plain decimals, `+ - * /`, unary signs, and parentheses. There are no functions, exponents, scientific notation, or implicit multiplication, which keeps the two evaluators small enough to agree. Formulas are stored in one canonical form, limited to 200 bytes as sent and as stored.

The client evaluates with mathjs in BigNumber mode, built from only its parser, walking the parse tree to allow the same node types. It computes each value as an exact fraction of BigNumber integers with enough precision that no digit is lost, rather than a BigNumber quotient, because a rounded quotient could round a result such as `1/3*0.015` differently from the server. Both evaluators run the same fixture file, `internal/money/testdata/formulas.json`, so a difference fails a test on one side.

A correction that omits a formula keeps the prior one only while it still equals the corrected amount; otherwise the formula is dropped rather than left describing a different amount. We rejected storing formulas in a separate table (more schema for evidence that belongs to one revision) and evaluating formulas only on the server (the person needs the result before saving).
