# T-005 Plan: Household Ledger Schema Migrations

## Summary

Implement T-005 by adding the first complete finance-domain Postgres schema as reviewable SQL migrations under `src/db/migrations`, while keeping identifier generation in application code instead of PostgreSQL.

This plan includes two important corrections:

- IDs should be ULIDs, not UUIDs
- ULIDs should be generated by a shared module in `./libs/`, not by PostgreSQL defaults

The outcome of T-005 should be:

- a stable relational schema for households, users, people, categories, accounts, origins, and transactions
- a clear final table contract that can be reviewed before implementation
- integration tests proving the schema works against the Docker-backed Postgres database

## Correction: ID Strategy

### Decision

Use ULIDs generated in application code, then convert them into UUID-compatible strings before writing them into Postgres `uuid` columns.

### Implementation direction

As part of the T-005 slice, add a shared ID utility in:

- [libs/id.ts](/Users/sifatul/coding/finance-tracker/libs/id.ts)
- [libs/id.test.ts](/Users/sifatul/coding/finance-tracker/libs/id.test.ts)

That module should:

- export a single ID creation function
- generate ULIDs
- format them in a UUID-like grouped string shape for readability

Example target shape:

- `01HZX4M6-7X8P-9K2Q-R4T6-8V1W2Y3Z4A5B`

This is still ULID-derived, but easier to visually scan in logs and database tables than one uninterrupted 26-character string.

### Why this matters for T-005

- every primary key column should be `uuid`
- migrations should not use `default gen_random_uuid()`
- later seed scripts, repositories, and route handlers should all generate IDs through `libs/id.ts`

### Design note

If we want to preserve sortability as much as possible, the formatter should only insert separators and uppercase the string, not change the encoded ULID characters themselves.

This helper should not land without direct unit test coverage because it becomes foundational infrastructure for seeds, repositories, and write paths.

Important domain rules already established:

- users belong to exactly one household in v1
- people are distinct from authenticated users
- categories are in scope and are household-scoped
- categories can be created from settings or inline during transaction creation
- manually created income and expense rows should have categories
- transfer-generated rows may omit `category_id`
- manual income rows require an origin
- transfer-generated income rows may omit `origin_id`
- transfers are paired ledger rows linked by a transfer grouping field
- money must be stored as integer minor units

## Final Proposed Schema

This section is the concrete schema proposal to review before implementation.

### 1. `households`

Purpose:

- root scope for household-owned data

Final proposed columns:

```sql
create table households (
  id uuid primary key,
  name text not null,
  description text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Constraints and indexes:

- consider `unique (name)` for operational clarity, unless we intentionally want duplicate household names

### 2. `users`

Purpose:

- invited and activated app-access users

Final proposed columns:

```sql
create table users (
  id uuid primary key,
  household_id uuid not null references households(id) on delete restrict,
  email text not null,
  name text,
  workos_user_id text,
  is_drafted boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (email)
);
```

Indexes:

```sql
create index users_household_id_idx on users (household_id);
create unique index users_workos_user_id_unique_idx
  on users (workos_user_id)
  where workos_user_id is not null;
```

### 3. `people`

Purpose:

- transaction attribution actors inside a household

Final proposed columns:

```sql
create table people (
  id uuid primary key,
  household_id uuid not null references households(id) on delete restrict,
  name text not null,
  is_default boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (household_id, name)
);
```

Indexes:

```sql
create index people_household_id_idx on people (household_id);
create unique index people_one_default_per_household_idx
  on people (household_id)
  where is_default = true;
```

### 4. `categories`

Purpose:

- household-scoped reusable transaction categories

Final proposed columns:

```sql
create table categories (
  id uuid primary key,
  household_id uuid not null references households(id) on delete restrict,
  name text not null,
  description text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (household_id, name)
);
```

Indexes:

```sql
create index categories_household_id_idx on categories (household_id);
```

### 5. `accounts`

Purpose:

- money-holding accounts such as cards, cash, and wallets

Final proposed columns:

```sql
create table accounts (
  id uuid primary key,
  household_id uuid not null references households(id) on delete restrict,
  name text not null,
  description text,
  initial_balance_minor bigint not null default 0,
  current_balance_minor bigint not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (household_id, name)
);
```

Indexes:

```sql
create index accounts_household_id_idx on accounts (household_id);
```

### 6. `origins`

Purpose:

- household-scoped income origins such as employers or clients

Final proposed columns:

```sql
create table origins (
  id uuid primary key,
  household_id uuid not null references households(id) on delete restrict,
  name text not null,
  description text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (household_id, name)

```

Indexes:

```sql
create index origins_household_id_idx on origins (household_id);
```

### 7. `transactions`

Purpose:

- unified ledger row for expenses, income, and transfer-generated entries
- stores the amount as an integer count of the smallest currency unit instead of a decimal

Final proposed columns:

```sql
create table transactions (
  id uuid primary key,
  household_id uuid not null references households(id) on delete restrict,
  account_id uuid not null references accounts(id) on delete restrict,
  person_id uuid not null references people(id) on delete restrict,
  category_id uuid references categories(id) on delete restrict,
  origin_id uuid references origins(id) on delete restrict,
  created_by_user_id uuid not null references users(id) on delete restrict,
  type text not null,
  amount_minor bigint not null,
  description text,
  transaction_date date not null,
  transfer_group_id uuid,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  check (type in ('income', 'expense')),

  check (amount_minor > 0),

  check (
    transfer_group_id is not null
    or category_id is not null
  ),

  check (
    type <> 'income'
    or transfer_group_id is not null
    or origin_id is not null
  )
);
```

Indexes:

```sql
create index transactions_household_id_idx on transactions (household_id);

create index transactions_household_date_idx
  on transactions (household_id, transaction_date desc, created_at desc);

create index transactions_household_person_idx
  on transactions (household_id, person_id);

create index transactions_household_account_idx
  on transactions (household_id, account_id);

create index transactions_household_category_idx
  on transactions (household_id, category_id);

create index transactions_household_origin_idx
  on transactions (household_id, origin_id);

create index transactions_household_transfer_group_idx
  on transactions (household_id, transfer_group_id)
  where transfer_group_id is not null;
```

### Why the transaction checks are shaped this way

- `category_id` is required unless the row is part of a transfer
- `origin_id` is required for manual income rows
- transfer-generated income rows are allowed to omit `origin_id`
- expenses always omit `origin_id`

This keeps the schema aligned with the current requirement and discovery docs without overcomplicating the first pass.

## Cross-Household Integrity Decision

This is the most important design choice in T-005.

### Simpler option

Use:

- normal foreign keys on `id`
- `household_id` columns on all household-scoped tables
- app-layer enforcement later to guarantee that referenced rows belong to the same household

Pros:

- cleaner SQL
- faster implementation
- easier to reason about for the first schema

Cons:

- Postgres will not fully guarantee same-household referential consistency across all transaction references

### Stronger option

Use composite uniqueness and composite foreign keys, for example:

- `(id, household_id)` unique on referenced tables
- composite foreign keys from `transactions` into `(account_id, household_id)`, `(person_id, household_id)`, etc.

Pros:

- DB-level enforcement of household scoping

Cons:

- much noisier schema
- more verbose inserts and constraints
- more moving parts for the first migration set

### Recommended choice for T-005

Default to the simpler option for this ticket:

- standard foreign keys
- explicit `household_id` columns
- application-layer household checks in future repository and route work

Reason:

- keeps T-005 reviewable
- gets the project moving
- still supports later hardening if we decide cross-household DB enforcement is worth the extra SQL complexity

## Risks

### 1. Over-constraining transfer rows

If we make category or origin requirements too strict, transfer-generated ledger rows will become awkward or impossible to represent.

### 2. Under-constraining manual transactions

If we leave too many fields nullable, later APIs will rely too heavily on app validation and we’ll lose the safety that this ticket is supposed to provide.

### 3. Household consistency gaps

With standard foreign keys alone, Postgres will not guarantee every referenced row belongs to the same household. That is a conscious tradeoff in the recommended T-005 shape.

### 4. ID generation consistency

Once we choose app-generated ULIDs, later tickets must use the shared `libs/id.ts` helper consistently. That needs to be part of the implementation discipline from T-005 onward.
