# T-003/T-004 Pivot Plan: Postgres via Bun SQL + Local Docker Dev DB

## Summary

Pivot the foundation data layer from SQLite to Postgres, starting by correcting the requirements and ticket docs so the backlog matches the new direction before implementation begins.

The implementation will **not** add a custom DB abstraction on top of Bun SQL. Instead:

- We create one Bun SQL connection module, cached for reuse.
- Route handlers and scripts import or receive that Bun SQL connection.
- Repositories/services stay DI-friendly by accepting `db` in their factory context, for example:
  `createUserRepository({ db, ...rest })`
- Testability comes from passing a real Bun SQL client in integration tests and a narrow mock/stub shape in unit tests where needed, rather than wrapping the client in a custom adapter layer.

  `db:dev:down`
  `db:dev:logs`

### 4. Implement T-004 with Bun SQL directly, but keep DI

- Add a single server DB module that creates the Bun SQL connection from env and caches it for reuse.
- The cached connection should be lazily initialized so route handlers do not reconnect on every invocation.
- Provide a separate connection creator for tests so integration tests can point at `TEST_DATABASE_URL`.
- Do not build a wrapper interface over Bun SQL.
- Repositories and services should accept a context object containing `db`, for example:
  `createUserRepository({ db, now, generateId })`
- Route handlers should either:
  import the shared cached `db`,
  or call a small `getDb()` helper and pass the result downward.
- Shared helpers added in T-004:
  UUID generation,
  UTC timestamp helper,
  money conversion helpers using integer minor units.

### 5. Add a SQL-first migration runner for Postgres

- Store ordered `.sql` migration files in a dedicated migrations directory.
- Add a migration tracking table with:
  `filename text primary key`
  `checksum text not null`
  `applied_at timestamptz not null default now()`
- The runner should:
  apply migrations in order,
  skip already-applied files,
  detect checksum drift,
  be safe to rerun,
  work against both dev and test databases.
- Use the Bun SQL connection directly in the migration runner too.
- Add scripts for:
  `db:migrate`
  `db:migrate:test`
- Keep seed data out of T-004; that remains T-006.

## Test Plan

- Unit tests for config/connection setup:
  missing `DATABASE_URL` fails clearly,
  test DB URL selection works,
  cached connection reuse behaves as expected.
- Unit tests for helper logic:
  UUID generation format,
  UTC timestamp formatting,
  money conversion round-trips and edge cases.
- Unit tests for repositories/services:
  factory functions accept `db` and other dependencies through context,
  pure business logic can be tested with stubs/mocks where DB behavior is not under test.
- Integration tests against Postgres:
  Bun SQL connects to the Docker test DB,
  basic query execution works,
  transaction commit works,
  transaction rollback works,
  migration runner applies ordered SQL correctly,
  rerunning migrations is a no-op,
  checksum drift is detected.
- Verification commands:
  `bun run format`
  `docker compose -f docker-compose.dev.yml up -d`
  `bun test`
  `bun run test:integration`
  `bun run lint`
  `bun run typecheck`
  `bun run build`
