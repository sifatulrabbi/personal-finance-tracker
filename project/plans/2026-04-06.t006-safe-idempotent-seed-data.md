# T-006 Plan: Safe Idempotent Seed Data

## Summary

Implement an explicit Bun seed workflow for the real and test households. The seed must create only required starter records and remain append-only in practice: insert missing rows, skip existing rows, and never update production data.

## Seed Records

- Real household: `Sifatul's Household`
- Test household: `Test Household`
- Real seed user: `mdsifatulislam.rabbi@gmail.com`
- Test seed user: `sifatuli.r@gmail.com`
- Default person for each household: `Household`
- Seed users start drafted with `is_drafted = true`, `name = null`, and `workos_user_id = null`.
- Use deterministic UUID constants for all seeded households, users, and default people.

## Implementation

1. Add `src/libs/server/db/seed.ts` with exported seed constants, result types, and `seedDatabase({ db })`.
2. Wrap seed writes in `db.begin(...)`.
3. Insert each row with `ON CONFLICT (id) DO NOTHING RETURNING id`.
4. Check household names before inserting because `households.name` is not unique; fail loudly when a seed household name exists under a different ID.
5. Treat returned rows as `inserted` and empty results as `skipped`.
6. Let natural-key conflicts under different IDs fail loudly rather than silently treating unexpected data as seeded state.
7. Add `src/scripts/db-seed.ts` with app DB and `--test` test DB modes.
8. Add `db:seed` and `db:seed:test` package scripts.
9. Add unit and integration tests that prove fresh seed, rerun idempotency, partial-state repair, no overwrite behavior, household-name conflict failure, and missing-migration failure.
10. Mark T-006 complete after verification passes.

## Out of Scope

- Seeding accounts, categories, origins, transactions, or example financial data.
- Running migrations from the seed command.
- Automatic app boot seeding.
- WorkOS auth implementation or UI changes.
