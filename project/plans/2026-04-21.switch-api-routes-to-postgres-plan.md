# Plan: Switch API Routes to Postgres (Retire mock-data.ts)

**Date:** 2026-04-21
**Status:** Proposed — awaiting approval before implementation
**Scope:** Backend only. No frontend contract changes (response shapes preserved).

---

## 1. Problem Statement

The Postgres layer exists but is **not actually used** for domain data. Today:

- Migrations run and a real connection is lazily opened (`src/libs/server/db/client.ts`).
- `resolveSessionUser` (`src/libs/server/auth/resolve-session-user.ts:45`) is the **only** code path that reads from the DB — it looks up `users` by email and activates drafted rows on first sign-in.
- **All 14 household CRUD route handlers read/write `src/libs/server/api/mock-data.ts`** (an in-memory array). On reload, process restart, or cold-start in production, every user mutation evaporates.
- The seed script only populates `households`, `users` (drafted), and a default `people` row per household. No `currencies`, `categories`, `accounts`, or `origins` are ever inserted — yet `transactions.original_currency_code` defaults to `'BDT'`, which doesn't exist in the `currencies` table for any household.

## 2. Goals

1. Every household-scoped route reads/writes Postgres through a thin repository layer.
2. `mock-data.ts` is **deleted**.
3. Balance changes, transfers, and transactional inline-creates (e.g. inline category on expense) run inside a single `db.begin` block — no partial writes on failure.
4. First-login user activation still works end-to-end (no regression).
5. A fresh `db:migrate && db:seed` produces a database where a seeded user can immediately sign in, create an account, create a category, record a BDT expense, and the data survives a server restart.
6. Migrations are corrected in-place (greenfield, zero users — no additive-only constraint).
7. Repository + route tests run against a real Postgres test database. The existing unit-test-with-mocks pattern is replaced.

**Non-goals:** UI work, WorkOS changes, deployment, multi-household membership, transaction editing UX changes, new endpoints.

## 3. Key Design Decisions

### 3.1 Procedural factory repositories with DI

Project CLAUDE.md: _"Follow proper DI in the backend coding, also stick to procedural coding instead of class based coding."_ **No classes, no `this`.** Each repository is a factory function that closes over the injected context and returns a plain object of async methods:

```ts
// src/libs/server/db/repository/accounts-repository.ts
import type { BunSqlDatabase } from "@/libs/server/db/client";

export type AccountsRepositoryContext = Readonly<{
  db: BunSqlDatabase;
}>;

export function createAccountsRepository(ctx: AccountsRepositoryContext) {
  const { db } = ctx;

  async function listByHousehold(householdId: string): Promise<AccountDto[]> {
    /* ... */
  }

  async function findById(args: {
    householdId: string;
    id: string;
  }): Promise<AccountDto | null> {
    /* ... */
  }

  async function insert(row: NewAccount): Promise<AccountDto> {
    /* ... */
  }

  // additional methods defined as local `async function` declarations above

  return {
    listByHousehold,
    findById,
    insert,
    /* ... */
  };
}

export type AccountsRepository = ReturnType<typeof createAccountsRepository>;
```

- The `ctx` object is always the first argument so future additions (logger, clock, feature flags) don't require a signature churn.
- The repository returns an object literal of free functions — no `class`, no prototype chain, no `this` binding.
- When a route needs a transaction, it calls `db.begin(async (tx) => { const accounts = createAccountsRepository({ db: tx }); /* ... */ })`. Repositories are cheap to instantiate because they're just closures over `ctx`.
- For route-handler convenience we add **one** helper in `src/libs/server/db/repository/index.ts`:

  ```ts
  export function createRepositories(ctx: { db: BunSqlDatabase }) {
    return {
      accounts: createAccountsRepository(ctx),
      categories: createCategoriesRepository(ctx),
      origins: createOriginsRepository(ctx),
      people: createPeopleRepository(ctx),
      currencies: createCurrenciesRepository(ctx),
      users: createUsersRepository(ctx),
      transactions: createTransactionsRepository(ctx),
    };
  }

  export type Repositories = ReturnType<typeof createRepositories>;
  ```

  Routes read this as `const repos = createRepositories({ db: getDb() });` or, inside a transaction, `createRepositories({ db: tx })`. Tests use the same factory against a test DB.

### 3.2 One repository file per table

Directory layout — every table in `src/db/migrations/` gets exactly one repository file:

```
src/libs/server/db/repository/
  accounts-repository.ts
  accounts-repository.test.ts
  categories-repository.ts
  categories-repository.test.ts
  currencies-repository.ts
  currencies-repository.test.ts
  origins-repository.ts
  origins-repository.test.ts
  people-repository.ts
  people-repository.test.ts
  transactions-repository.ts
  transactions-repository.test.ts
  users-repository.ts
  users-repository.test.ts
  index.ts                       // exports createRepositories + all factories + all Repository types
```

`resolve-session-user.ts` is refactored to go through `users-repository.ts` so there's one place that knows the `users` schema.

Balance-mutation side-effects for transfers and amount edits live inside `transactions-repository.ts`, which takes a reference to `accounts-repository` via `ctx` so the same open transaction is reused:

```ts
export function createTransactionsRepository(ctx: {
  db: BunSqlDatabase;
  accountsRepository: AccountsRepository; // bound to the same db/tx
}) {
  /* ... */
}
```

The `createRepositories` helper wires this up automatically.

### 3.3 Atomicity boundary

Every mutating route runs `db.begin(async (tx) => { ... })` and constructs repositories against `tx`. In particular:

- Creating an expense with `categoryName` (inline create) = `INSERT categories` + `INSERT transactions` in one transaction.
- Creating income with `categoryName` / `originName` = potentially three inserts in one transaction.
- Creating a transfer = two `INSERT transactions` + two `UPDATE accounts.current_balance_minor`, one transaction.
- Updating a transaction that changes `accountId` or `amount` = one `UPDATE transactions` + compensating `UPDATE accounts` pair, one transaction.
- Deleting a transaction reverses its balance delta, same transaction.

### 3.4 Response shape is the existing mock shape

The existing `Mock*` types in `mock-data.ts` become the canonical response DTOs, renamed (`AccountDto`, `TransactionDto`, …) and moved to `src/libs/server/api/dto.ts`. The frontend stores already consume that shape; if we change it, we break the UI. Internal row types (`AccountRow` etc.) differ from DTOs — the repositories return DTOs so routes don't do per-row mapping.

### 3.5 Balance invariants live in the repository, not the route

`transactions-repository.ts` exposes `insertExpense`, `insertIncome`, `insertTransfer`, `update`, and `delete` as the only public surface. Each method internally adjusts `accounts.current_balance_minor`. Route handlers never issue a raw `UPDATE accounts` during transaction flows. This keeps the "one expense means one debit" rule enforceable from one place.

## 4. Migration Fixes (greenfield, rewrite in place)

Project CLAUDE.md explicitly allows this: _"You can make any changes to the database schema or existing migrations without worrying for repercussions."_ Zero users exist.

### 4.1 Merge 0008 + 0010 into a single 0008

`0010-add-currency-to-transactions.sql` is eliminated. `0008-create-transactions.sql` defines `original_currency_code`, `original_amount_minor`, `exchange_rate_to_bdt_minor` from day one. Rationale: the split only existed because we pretended we had users.

### 4.2 Foreign-key `transactions → currencies`

Add to the rewritten 0008:

```sql
CONSTRAINT transactions_currency_fk FOREIGN KEY (household_id, original_currency_code)
  REFERENCES currencies (household_id, code) ON DELETE RESTRICT
```

This requires the existing `currencies_household_code_unique` index (already present in 0009). The migration order becomes: currencies before transactions, i.e. what is today `0009-create-currencies.sql` becomes `0008-create-currencies.sql`, and transactions moves to `0009-create-transactions.sql`.

### 4.3 One base currency per household

Add to the renumbered 0008-currencies:

```sql
CREATE UNIQUE INDEX currencies_one_base_per_household_idx
  ON currencies (household_id)
  WHERE is_base = TRUE;
```

Mirrors the existing `people_one_default_per_household_idx` pattern.

### 4.4 Final migration layout after rewrite

| #    | File                                                      |
| ---- | --------------------------------------------------------- |
| 0001 | `enable-pgcrypto.sql` (unchanged)                         |
| 0002 | `create-households.sql` (unchanged)                       |
| 0003 | `create-users.sql` (unchanged)                            |
| 0004 | `create-people.sql` (unchanged)                           |
| 0005 | `create-categories.sql` (unchanged)                       |
| 0006 | `create-accounts.sql` (unchanged)                         |
| 0007 | `create-origins.sql` (unchanged)                          |
| 0008 | `create-currencies.sql` (was 0009 + base-unique index)    |
| 0009 | `create-transactions.sql` (was 0008 + 0010 + currency FK) |

Existing dev DBs must be recreated. The `migrations_log` table's checksum guard (`src/libs/server/db/migrations.ts:80`) will refuse to run if an old 0008 is already recorded. Document a one-line reset in the PR description: `bun run db:dev:down -v && bun run db:dev:up && bun run db:migrate && bun run db:seed`.

### 4.5 Decisions deferred (noted, not changed now)

- `ON DELETE RESTRICT` vs `CASCADE` for household-scoped FKs — current `RESTRICT` is kept as a prod safety net.
- `transactions.type` CHECK vs Postgres enum — CHECK stays; enums complicate later additions (e.g. `'adjustment'`).
- A `household_members` join table to support multi-household membership — explicitly out of scope per `00-discovery.md:34` and the single-household assumption.

## 5. Seed Strategy Update

Extend `src/libs/server/db/seed.ts` so a fresh seed leaves each household **able to record a transaction in BDT**. Bootstrap per household inside the existing `db.begin`:

1. Household row (unchanged).
2. Drafted user row (unchanged).
3. Default `Household` person (unchanged).
4. **NEW:** A single BDT currency row — the app's default base currency — `code = 'BDT'`, `symbol = '৳'`, `name = 'Bangladeshi Taka'`, `rate_to_bdt_minor = 100`, `is_base = true`.

No other currencies are seeded. Additional currencies (USD, EUR, anything else) are created by the household from the settings page; the mock fixtures did that only for UI previews and are not a bootstrap requirement.

Idempotency: each insert uses `ON CONFLICT (id) DO NOTHING RETURNING id`, matching the existing pattern. The BDT currency gets a deterministic UUID per household stored on `SEED_HOUSEHOLDS[...].baseCurrency = { id, code: 'BDT', ... }` so it is auditable and rerunnable. The new `currencies_one_base_per_household_idx` (section 4.3) guarantees no duplicate base rows can slip in.

**Not seeded:** `categories`, `accounts`, `origins`, `transactions`, and any non-BDT currency. Users create these through the UI.

The seed integration test (`src/test/integration/seed.integration.test.ts`) gets additional assertions: exactly one BDT row per household, `is_base = true`, `rate_to_bdt_minor = 100`, and rerunning the seed does not produce a second base currency.

## 6. Repository Specifications (signatures only — implementation in PR)

```ts
// accounts-repository.ts
listByHousehold(householdId)                → AccountDto[]
findById({ householdId, id })               → AccountDto | null
insert({ householdId, name, description, initialBalanceMinor })
                                            → AccountDto
update({ householdId, id, patch })          → AccountDto
adjustBalance({ householdId, id, deltaMinor }) → void  // used by transactions repo
delete({ householdId, id })                 → void

// categories-repository.ts / origins-repository.ts / people-repository.ts
listByHousehold(householdId)                → Dto[]
findById(...)                               → Dto | null
upsertByName({ householdId, name })         → Dto   // inline-create helper
insert(...)                                 → Dto
update(...)                                 → Dto
delete(...)                                 → void

// currencies-repository.ts
listByHousehold(householdId)                → CurrencyDto[]
findByCode({ householdId, code })           → CurrencyDto | null
findBase(householdId)                       → CurrencyDto          // throws if missing
insert(...)                                 → CurrencyDto
update(...)                                 → CurrencyDto
delete({ householdId, id })                 → void                 // refuses when is_base=true

// users-repository.ts
findByEmail(email)                          → UserRow | null
activateDrafted({ id, workosUserId, name }) → void
insertInvite({ householdId, email })        → UserDto               // POST /users

// transactions-repository.ts
listByHousehold({ householdId, filters, page, pageSize }) → { data: TransactionDto[]; total: number }
findById({ householdId, id })               → TransactionDto | null
insertExpense(cmd: InsertExpenseCommand)    → TransactionDto
insertIncome(cmd: InsertIncomeCommand)      → TransactionDto
insertTransfer(cmd: InsertTransferCommand)  → { expense: TransactionDto; income: TransactionDto; transferGroupId: string }
update({ householdId, id, patch })          → TransactionDto
delete({ householdId, id })                 → void                 // removes transfer pair when transfer_group_id set
```

All repository methods accept a `BunSqlDatabase` at the factory level, so the caller controls whether they're running inside a `db.begin` transaction.

## 7. Route Rewrites (per-route notes)

Mostly mechanical — replace `mockX.filter / find / push / splice` with repo calls — but a few routes have real logic changes:

- `POST /transactions/expenses` / `POST /transactions/income`: **inline category/origin create** becomes `categoriesRepository.upsertByName` inside the transaction. Today it fabricates an ID and doesn't persist.
- `POST /transfers`: wraps `transactionsRepository.insertTransfer` in `db.begin`. Two transaction inserts + two balance adjustments.
- `PATCH /transactions/[id]`: amount/account changes reverse the original balance deltas and apply new ones in the same transaction. Today the mock silently loses this invariant.
- `DELETE /transactions/[id]`: reverses balance deltas; removes the transfer pair atomically.
- `POST /households/[h]/users`: actually `INSERT` a drafted `users` row instead of logging and returning a fake object.

Route error paths stay identical (same `ApiError` codes, same user messages).

### 8.1 Delete

- All 14 `*.test.ts` files next to route handlers that assert against mock state. They'll be replaced.

### 8.2 Keep

- `seed.integration.test.ts` (extended with currency assertions).
- Existing `libs/server/db/*.test.ts` unit tests for client, migrations, migration-repository.
- `libs/server/auth/*` tests (but pointed at the users repo).
- `libs/server/api/{access,errors,schemas,validation}.test.ts` — these are pure-logic, no mock-data coupling.

### 8.3 Add

- **Repository unit tests** (`src/libs/server/db/repository/*.test.ts`): one file per repository. Run against the test DB (`createTestDb`), per-test schema reset via the existing `resetPublicSchema` helper pattern in `seed.integration.test.ts`. Each test asserts a single repo invariant — e.g. `insertExpense adjusts account balance by -amountMinor`, `delete of transfer removes both ledger entries`.
- **Route integration tests** (`src/app/api/.../route.integration.test.ts`): one per route, calls the handler directly with `Response`/`Request` objects, hits the real test DB. Run under `bun run test:integration`. Cover the happy path + one error path (403 cross-household, 404, validation). This replaces the deleted unit tests.
- **End-to-end bootstrap test** (`src/test/integration/bootstrap.integration.test.ts`): fresh DB → migrate → seed → simulate sign-in for a seeded user → insert an account → insert a category → insert an expense via the repository/route → assert balance and list outputs. This is the one test that would catch a regression in any of steps 4–7 above.
- **Cross-household isolation test** for the transactions route (one household must not read another's rows).

### 8.4 Test infrastructure

- Add `src/test/helpers/database.ts` exporting `resetPublicSchema(db)`, `applyMigrationsAndSeed(db)`, `createRepositories(db)`. Reuses the same pattern already used by `seed.integration.test.ts`.
- Route integration tests import the route's `GET`/`POST` directly, bypassing Next's runtime. Build `new NextRequest(...)` and inspect the returned `Response`.

### 8.5 CI impact

- `bun test` still runs only unit tests (fast, no Docker). `bun run test:integration` runs the DB-backed tests. Both should be green locally before merge; CI runs both.

## 9. Implementation Phases (suggested commit split)

1. **chore(db): merge transactions + currency migration, add base-currency unique index, reorder 0008/0009.** (Migration rewrite + migrations.ts untouched. Dev DB reset documented.)
2. **feat(db): seed BDT/USD/EUR per household.** (`seed.ts` + test updates.)
3. **feat(db): add repositories and DTO module.** (`src/libs/server/db/repository/*`, `src/libs/server/api/dto.ts`, repository unit/integration tests.)
4. **ref(auth): move users DB access into users-repository.** (Refactor `resolve-session-user.ts` and `POST /users` to use repo.)
5. **ref(api): accounts, categories, origins, people, currencies routes use DB.** (One commit per domain is fine — each is independent and low-risk. Keep them separate so revert is cheap.)
6. **ref(api): transactions GET + PATCH + DELETE use DB.**
7. **ref(api): transactions/expenses, transactions/income, transfers use DB with transactional balance updates.**
8. **ref(api): delete `mock-data.ts` and all mock-based route tests.** (This is the commit that makes the app actually depend on Postgres. Should be the last breaking step.)
9. **test(int): add bootstrap integration test and cross-household isolation test.**
10. **chore: `bun run format` + `bun run lint` + `bun run typecheck`.**

Each commit is independently reverting-safe because later commits introduce the new code paths before the old ones are deleted.

## 10. Risks and Mitigations

| Risk                                                                                       | Mitigation                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dev DB has old migration checksums → migrate refuses to run                                | PR body documents the one-line reset; no active users means zero data loss.                                                                                                             |
| Route integration tests are slow and flake CI                                              | Per-test schema reset is fast (<50ms). Each test owns its data. Keep file-level `beforeAll` for migration apply + seed.                                                                 |
| Response shape drift breaks frontend silently                                              | Route integration tests assert the full DTO shape. Plus an E2E test through the real store in a later PR (out of scope here).                                                           |
| Transfer edits double-apply balance deltas                                                 | `PATCH` rejects edits to transfer transactions (already enforced — `route.ts:86`); this stays.                                                                                          |
| Balance drift from concurrent inserts                                                      | All balance mutations are inside `db.begin` with `SELECT ... FOR UPDATE` on the account row before adjusting. Add a helper `accountsRepository.adjustBalance` that uses row-level lock. |
| Seed script silently fails when currency table doesn't yet exist during partial migrations | `seedDatabase` already runs in a single `db.begin`; migrations apply before seed in practice. Integration tests cover the ordering.                                                     |
